# Written Questions Q4–Q20

## Q4 – Test-automation architecture and maintainability

A maintainable automation suite separates application setup, test intent, reusable helpers,
and reporting. In this repository, Express and WebSocket responsibilities live under Q1,
while Playwright specifications declare observable browser behavior. Locators should prefer
roles and accessible names, then labels or stable test IDs. Assertions must verify a final
state, not merely the absence of an error or a successful log line. Dynamic synchronization
uses `waitForFunction` and Playwright `expect` polling because DOM and network timing are
unpredictable. Fixed sleeps should be avoided except when a requirement explicitly measures
elapsed wall-clock behavior. Configuration should isolate URLs, ports, secrets, retries,
reports, and screenshots. A clean suite also starts and stops external processes within the
test runner, producing repeatable evidence.

## Q5 – Web and WebSocket testing

WebSocket testing requires separating transport delivery from application state. A test
should verify connection establishment, packet schema, sequence information, drop behavior,
latency, reconnection, and UI rendering. Q1 generates packets on `/stream`, applies server
jitter, drops packet numbers divisible by four, and exposes counters through a REST health
endpoint. Playwright intercepts the socket for deterministic observation. Assertions cover
jitter between 2000 and 7000 milliseconds and the synchronized DOM state. Packet loss must
not be confused with UI inactivity: the browser should remain connected and continue to
process later packets. Cleanup is important because open sockets and intervals can keep
servers alive after a test completes.

## Q6 – Dynamic synchronization

A dynamic guardian observes application state instead of sleeping. Q1's guardian waits for
`data-state-sync=synchronized`, hidden loading content, and a valid canvas. The state is set
only after a valid WebSocket packet has been received, so an open socket alone is insufficient.
This pattern avoids timing assumptions and remains stable across CPU or network variations.
Timeouts are failure boundaries, not synchronization delays. Tests should also assert that
the synchronized state is maintained after later packets rather than only checking one
transient DOM mutation.

## Q7 – Race conditions and triple-click testing

Triple-click behavior should measure event timing while also preventing duplicate operations.
Q1 dispatches clicks across three animation-frame callbacks, producing a 30–120 millisecond
sequence, and verifies the elapsed value. The UI uses an `operationInFlight` guard so extra
clicks do not launch parallel retries. This is more meaningful than replaying a static pause:
it verifies both timing and exclusivity. Race tests should assert one server operation, no
duplicate state transitions, and a single terminal result.

## Q8 – Retry and exponential backoff

Retries are for transient failures, not every error. Q1 calls the review endpoint, performs
exponential backoff of 100, 200, 400 milliseconds and subsequent waits, and records each
attempt. Permanent validation, authorization, or replay failures should fail immediately.
Backoff should include jitter in distributed systems to reduce synchronized traffic, although
jitter was separately specified for the streaming packets. Tests must verify attempts,
delays, terminal success, and retry counts through observable state.

## Q9 – Circuit breaker

The circuit-breaker pattern has CLOSED, OPEN, and HALF-OPEN states. CLOSED permits operations;
OPEN blocks calls after repeated failures; after a cooldown, HALF-OPEN permits a controlled
probe. Q1 exposes `data-circuit-state` and transitions OPEN to HALF-OPEN to CLOSED after a
successful probe. A probe failure returns the breaker to OPEN. Production implementations
should use failure thresholds, reset deadlines, monotonic clocks, concurrency-safe counters,
and metrics. The in-browser demonstration is intentionally local and does not replace a
server-side distributed breaker.

## Q10 – Payload interception and malformed input

Network interception can capture and replace a request only in the test environment. Q1
intercepts a malformed precision string, preserves the original for evidence, changes it to
`12.34`, and continues the request. The server validates precision and amount with strict
types and bounds; malformed input returns HTTP 400 plus a machine-readable error. UI code
surfaces the rejection in a status region and toast rather than crashing. Tests verify both
the intercepted transformed payload and direct rejection of the unmodified malformed payload.

## Q11 – API test data and runtime entity identity

API tests should create resources with POST, extract the runtime ID from JSON, and use that
ID in subsequent PUT URLs and headers. Q2 follows this pattern. The entity is stored in a
server-side map and cannot be modified until it exists. Testing should cover a known ID,
unknown ID, mismatched URL/header ID, malformed JSON, successful update, and repeated update.
Runtime extraction prevents brittle hard-coded identifiers and makes test behavior portable.

## Q12 – HMAC-SHA256 and exact raw-body signing

HMAC-SHA256 signs a canonical payload that includes an exact timestamp, runtime entity ID,
and raw UTF-8 request body. Q2 uses `${timestamp}\n${entityId}\n${rawBody}`. Whitespace,
property order, line endings, and numeric formatting in the body remain significant. The
request must therefore preserve bytes and sign before JSON serialization or reformatting.
Only lowercase or valid hexadecimal signature representations should pass format validation.
The implementation never logs or tests with a real secret.

## Q13 – Constant-time verification and replay prevention

Constant-time comparison prevents timing characteristics from revealing where a signature
differs. Q2 parses the header into a fixed 32-byte buffer and uses
`crypto.timingSafeEqual` before replay checking. Timestamp freshness is checked within an
absolute 300-second window. A replay key combines timestamp and signature; successful exact
replays receive HTTP 409. Persisting replay state requires a distributed cache and retention
policy in production rather than the in-memory demonstration map.

## Q14 – HTTP rejection semantics

APIs should distinguish request, authentication, resource, and replay failures. Q2 uses:
201 for creation, 200 for valid modification, 400 for malformed headers or JSON and ID
mismatch, 404 for unknown entities, 401 for invalid signatures or stale timestamps, and
409 for replay. These codes allow clients and automation to choose specific recovery actions.
Error bodies use stable machine-readable names rather than depending on implementation text.

## Q15 – CI/CD and security testing

Automation should run in a clean environment with pinned lockfiles, explicit environment
variables, isolated ports, and termination of child processes. HMAC secrets belong in CI
secrets and must not be committed. CI stages can install dependencies, run API tests, run
browser tests, publish Playwright reports, and retain failure traces. A security gate should
fail on signature, freshness, tampering, replay, or malformed-JSON regressions. Dependencies
and browser binaries should be cached where policy permits.

## Q16 – Accessibility and semantic locators

Semantic locators use accessibility roles and names so tests follow user intent rather than
CSS structure. Examples include `getByRole("button", { name: "Execute review" })` and
`getByLabel("Open name")`. Status regions should expose updates through `aria-live` or roles
such as `status` and `alert`. Q1 uses explicit test IDs for state instrumentation, but
accessible locators remain available for user-facing controls. Q3 demonstrates open Shadow
DOM traversal and explains that closed roots require retained references or supported test
instrumentation.

## Q17 – Shadow DOM inspection

An open Shadow DOM root is accessible through `host.shadowRoot` and Playwright shadow-piercing
locators. A closed root is intentionally hidden from `closedHost.shadowRoot` and ordinary
selectors. The creating JavaScript scope may retain the original returned reference, but
external automation cannot reliably obtain it later. Supported alternatives are an existing
root reference, Chrome DevTools Protocol integration, an application test seam, or component
instrumentation. A closed root should not be described as globally inaccessible in every
tooling context; it is inaccessible through ordinary DOM APIs unless another supported access
mechanism exists.

## Q18 – Reporting and evidence

Evidence should be reproducible and truthful. Q1 generates an HTML Playwright report and
configures screenshots for failure and an explicit dashboard screenshot in the successful
suite. Q2 terminal output includes assertions and durations. Q3 uses a Playwright browser
test and screenshot. The repository's [execution results](../docs/execution-results.md)
record commands, pass counts, and limitations. Videos, screenshots from social media, PDFs,
and external submissions must not be represented as generated until the user performs those
actions. Reports are evidence only when they correspond to an actual run.

## Q19 – Compulsory AI-native engineering answer

An AI-native engineer uses AI to accelerate requirements clarification, test design,
implementation, and diagnosis, while retaining engineering accountability for correctness.
In this assignment, AI assistance is useful for proposing edge cases such as replay,
tampering, packet loss, and circuit-breaker transitions. It is not a substitute for running
the code or inspecting evidence. Prompts should state architecture, constraints, expected
outputs, and security boundaries. Generated code requires focused tests and human review for
timing, cryptographic mistakes, and harmful assumptions. Unverified results must be marked
unknown rather than reported as complete. Responsible use includes avoiding secrets in
prompts, reviewing licenses and dependencies, tracing generated changes, and documenting
limitations. Ambiguity is solved through source evidence, local experiments, explicit
assumptions, and stakeholder clarification. The engineer remains responsible for the final
system.

## Q20 – Submission quality and known limitations

A strong submission separates source implementation, automated evidence, written answers,
and manual artifacts. It includes exact setup commands, environment-variable instructions,
ports, tests, reports, and a known-limitation section. Q1 is limited by an in-memory browser
demo and does not prove production network packet loss. Q2 replay state is in-memory and
does not demonstrate distributed secret management. Q3 closed-root access depends on
instrumentation or browser tooling. The repository should not claim successful social
engagement, recordings, or uploads that do not exist. Final manual work is clearly
identified for the owner.
