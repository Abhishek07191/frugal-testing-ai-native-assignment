# Q19 – Compulsory: How I Would Work as an AI-Native Software Engineer

I would treat generative AI as an engineering multiplier rather than an authority. During
requirements analysis, I would ask it to enumerate ambiguity, failure modes, test matrices,
and security assumptions, while comparing every claim with the repository and assignment
source. During implementation, I would keep changes small and type-safe, preserve existing
patterns, and use tests to prove behavior. During debugging, AI may propose hypotheses, but
the evidence for a fix must come from logs, browser state, HTTP responses, or reproducible
tests.

Responsible use starts with data handling: no credentials or customer information enters a
prompt unless an authorized system permits it. I would avoid pasting secrets and verify that
generated code uses environment variables, constant-time cryptographic comparisons, strict
input validation, and standard HTTP semantics. AI-generated dependencies require license and
provenance checks. Generated diagrams or screenshots should not be presented unless the
underlying system produced them.

My approach to an ambiguous problem is to identify missing inputs, define measurable
acceptance criteria, isolate one experiment, and document assumptions. In this assignment,
for example, packet jitter and drop percentage can be measured from actual packet numbers;
API replay can be proved by sending an identical signed request twice. Ambiguity about the
detailed Q4–Q20 sub-questions is not resolved by inventing answers; the original prompt must
be supplied.

AI can improve learning by explaining a concept, generating an initial test case, or
suggesting a refactor. The engineer remains responsible for semantic correctness, maintainers'
needs, performance, privacy, and operational risk. The final quality signal is observable
behavior under tests and honest reporting of limitations.
